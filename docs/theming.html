Make it yours

A theme is design tokens. Nothing else.

No component CSS is touched, no selector is more specific than :root, and nothing needs !important - which is what makes adopting this framework in a new product a one-line change rather than an afternoon of overrides.

Switching a theme

Load the core stylesheet, then a theme. Swapping the second line changes every screen in the product.

<link rel="stylesheet" href="/static/ui-framework/dist/ui-framework.min.css">
<link rel="stylesheet" href="/static/ui-framework/dist/themes/default.min.css">

Themes are built separately and are not part of the core bundle. A framework used by more than one product should not ship one product's palette in the shared artefact - that is how a shared framework stops being shareable.

Making one for your project - no build step

You do not need to rebuild the framework to use your own theme. A theme is an ordinary stylesheet containing custom properties and nothing else, so it lives in your project, is served by your application, and is deployed on your release cycle. The framework never has to know it exists.

<link rel="stylesheet" href="/static/ui-framework/dist/ui-framework.min.css">
<link rel="stylesheet" href="/static/css/acme-theme.css">   <!-- yours -->

That is the whole procedure. Copy src/themes/default.css as a starting point if you like, or write the handful of tokens from The minimum worth changing straight into a stylesheet you already have. It does not need a separate file, a particular filename, or a place in this repository.

Then when would you touch build.py? Only if you want the framework itself to distribute your theme - that is, to publish it in dist/themes/ alongside default and forest for other projects to consume. The THEMES list exists to minify the worked examples this repository ships. It is not a registry a theme has to be entered in to work.

The one rule: your theme must come last

The framework's defaults are declared at :root, and so are yours. Equal specificity means source order decides - a theme linked before the bundle loses every token to the defaults and appears to do nothing at all. There is no warning; the page simply looks unthemed.

If you cannot control the order - a parent layout or a Tiles definition owns the <head>, say - use ui-framework.layered.css instead. Its tokens sit inside @layer ui-base, and unlayered CSS always beats layered CSS regardless of position, so your theme wins wherever it lands.

Change the values, leave the names alone. Token names are the contract between a theme and every component. Rename one and whatever consumed it silently loses its styling - there is no error, just a button that has gone grey.

The minimum worth changing

If you touch nothing else, these five give you a coherent theme. Everything else has a sensible default.

:root {
  --ui-primary:        #0b6e4f;   /* buttons, links, focus rings, active nav */
  --ui-primary-hover:  #0a5f45;   /* about 8% darker  */
  --ui-primary-active: #084c37;   /* about 15% darker */
  --ui-primary-soft:   #e9f5f0;   /* tints: selected rows, soft badges */
  --ui-primary-100:    #d2ebe2;   /* borders on those tints */
}

Two more are worth setting because they are the most visible surfaces after the primary: --ui-nav-bg (the navigation rail) and --ui-chart-1 (the first chart series).

Overriding without writing a theme

Tokens cascade like any other custom property, so you can override them at any scope. This is the escape hatch for the cases a theme file is too blunt for.

Adjust a theme you have loaded

Put your overrides in a stylesheet loaded after the theme. Both are plain :root declarations, so the later one wins - no specificity contest.

<link rel="stylesheet" href="dist/ui-framework.min.css">
<link rel="stylesheet" href="dist/themes/default.min.css">
<link rel="stylesheet" href="/static/css/app.css">

/* app.css */
:root {
  --ui-primary: #7c3aed;      /* keep the theme, change the accent */
  --ui-radius-3: 4px;         /* squarer cards than the theme ships */
}

One region only

Useful for a multi-tenant screen, or a panel that belongs to another service.

<section style="--ui-primary:#6d28d9; --ui-primary-soft:#f5f3ff">
  <button class="ui-btn ui-btn-primary">Purple in here only</button>
</section>

By environment

A staging site that cannot be mistaken for production is worth more than any banner. One token does it.

body.is-staging { --ui-nav-bg: #7f1d1d; }

At runtime

document.documentElement.style.setProperty("--ui-primary", tenant.colour);

// charts are drawn, not styled, so re-render them after a token change
UI.qa("[data-ui-chart]").forEach(UI.chart.refresh);
That last line is the one thing tokens do not reach on their own. SVG charts read their palette at render time, so a colour changed after they were drawn needs UI.chart.refresh(). Everything else - CSS-styled - updates instantly.

Dark mode

The framework ships a dark palette, but a theme that sets brand tokens at :root overrides it. If your theme changes the primary, it has to supply the dark variant too - otherwise a theme switch produces light-mode brand colours on a dark surface. Technically working, visibly wrong.

[data-ui-theme="dark"] {
  /* lift the primary -  a dark surface eats saturation */
  --ui-primary: #2f9e73;
  --ui-primary-soft: #10261f;
  --ui-surface: #111827;
  --ui-text: #e5edf7;
}

Switch with <html data-ui-theme="dark">, or give the user the built-in toggle: <button data-ui-theme-toggle> - the button in this page's header is one.

Three things worth knowing before you pick colours

Neutrals are not neutral

Give greys a cast that agrees with the primary - slate against green, warm grey against red. A true #808080 beside a strong primary is the single most common reason a palette looks like a default nobody chose.

Density is two values

Shrinking --ui-font-size without bringing --ui-control-* down with it leaves padding that looked right at 16px looking careless at 13.6px. Move them together or not at all — try the Forest, dense preset above and then imagine it with the original control heights.

Contrast is yours to check

The framework meets WCAG 2.1 AA for its own defaults; it cannot check yours. A primary that fails against white fails on every button in the product at once. Check it before you commit, not after someone reports it.

Alongside Bootstrap or an existing stylesheet

Use the layered build so precedence is explicit instead of a specificity race.

<link rel="stylesheet" href="dist/ui-framework.layered.min.css">
<link rel="stylesheet" href="dist/themes/default.min.css">

/* your stylesheet */
@layer app-reset, ui-base, ui-components, ui-utilities, app-overrides;

Anything you put in app-overrides then beats the framework regardless of selector specificity. Note that an unlayered stylesheet always outranks a layered one, so keep your own overrides in a declared layer too.
