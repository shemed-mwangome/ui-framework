Single-page frameworks

No wrapper library. One line of setup.

This framework is markup plus data-ui-* attributes, and it exposes the two lifecycle hooks a component framework needs: initialise a subtree, tear a subtree down. Angular already tells you when those happen, so the integration is a single call, not a component per widget.

Setup

Three things, once per application. The bundle is a plain script that assigns window.UI, so it is loaded as a global asset rather than imported as a module.

1. Load the CSS and JS as global assets in angular.json. Use the layered stylesheet if the application also loads Bootstrap, CoreUI or an existing master.css. See using alongside Bootstrap for which build to pick.

"styles": [
  "node_modules/ui-framework/dist/ui-framework.css"
],
"scripts": [
  "node_modules/ui-framework/dist/ui-framework.min.js"
]

2. Start the observer once the application has bootstrapped.

// main.ts
bootstrapApplication(AppComponent, appConfig)
  .then(() => UI.observe(document.body));

In a large application, register it outside Angular’s zone so DOM insertions do not each schedule a change-detection pass:

export function provideUiFramework(): EnvironmentProviders {
  return makeEnvironmentProviders([
    provideAppInitializer(() => {
      const zone = inject(NgZone);
      zone.runOutsideAngular(() => UI.observe(document.body));
    }),
  ]);
}

3. Pick up the types by adding the package to tsconfig.app.json: "types": ["ui-framework"]. See TypeScript below.

Why one line is enough

UI.observe(root) watches for inserted and removed nodes and calls UI.init() and UI.destroy() on them, batched on an animation frame. That covers every way Angular puts markup on the page: @if and @for, *ngIf and *ngFor, router navigation, lazily-loaded routes, dialogs: without a directive on any template.

Teardown matters as much as setup. Components register cleanup with UI.cleanup(), and some of them attach listeners outside their own subtree: an open dropdown or picker registers a capture-phase scroll handler on window so it can reposition. Destroying a route without releasing that leaves a handler running on every scroll for the life of the page. The observer releases it for you.

i
Initialising twice is harmless

Every module guards on a data-ui-*-ready flag, so an extra UI.init() over already-built markup does nothing. You never need to check whether a region has been initialised before calling it.

Binding to reactive forms

Every input-bearing component keeps the real <select> or <input> you wrote and drives it, rather than replacing it with a widget of its own. So formControlName, ngModel and [(ngModel)] bind directly to framework markup, with no ControlValueAccessor to write.

<select multiple data-ui-multiselect data-display="tags"
        data-placeholder="Select reviewers" data-search="true"
        formControlName="reviewerIds">
  @for (reviewer of reviewers(); track reviewer.uuid) {
    <option [value]="reviewer.uuid">{{ reviewer.name }}</option>
  }
</select>

<div class="ui-date-picker" data-ui-date-picker data-ui-placeholder="Select date">
  <input type="date" formControlName="issuedDate">
</div>

That works because of what the components dispatch on the control they own. Angular’s built-in value accessors each listen for one specific event, and a widget that fires the wrong one updates the DOM while leaving the form model untouched: the field looks filled and submits empty. The framework fires the pair a browser fires for a real edit:

Angular accessorApplies toListens for
DefaultValueAccessortext input, textareainput, blur
NumberValueAccessorinput[type=number]input, blur
SelectControlValueAccessorselectchange, blur
SelectMultipleControlValueAccessorselect[multiple]change, blur
CheckboxControlValueAccessorinput[type=checkbox]change, blur
RadioControlValueAccessorinput[type=radio]change, blur

Note the split: a <select> is driven by change, but a text input is driven by input and ignores change entirely. That is why the date picker and date range, which write a formatted date into a text input, dispatch both. Anywhere a component writes a value on the user’s behalf it calls UI.fireChange(element), which emits a bubbling input followed by a bubbling change.

!
Setting a masked value from code does not notify the form

UI.mask.set(field, value) writes the formatted value straight to the field without dispatching anything, on the assumption that code which sets a value already knows it did. Under Angular, prefer setting the FormControl instead: or call UI.fireChange(field) afterwards if you must write to the DOM.

Server-side validation errors bind through UI.validate.showErrors(), which accepts either shape a JSON error body usually takes:

this.api.save(form.value).subscribe({
  error: (response) => {
    UI.validate.showErrors(this.formEl.nativeElement, response.error.errors);
    // { licenceNo: "Already taken" }  or  [{ field, message }, ...]
  },
});

Options and rows that arrive late

This is the one place the integration needs help. A component builds when its element is inserted. If the element is inserted empty and Angular fills it from an HTTP response a moment later, the component built against nothing.

Every affected component exposes a refresh that rebuilds it from the current DOM:

reviewers = signal<Reviewer[]>([]);

ngOnInit() {
  this.api.reviewers().subscribe((list) => {
    this.reviewers.set(list);
    // After Angular has rendered the new <option> elements.
    afterNextRender(() => UI.multiselect.refresh(this.select.nativeElement));
  });
}

UI.table.refresh(), UI.selectList.refresh(), UI.chart.refresh() and UI.combobox behave the same way.

The alternative is to not have the problem: several components can fetch their own data, in which case the framework owns both the request and the render and Angular never touches the rows. See data-ui-url on tables and charts, and remote option loading on the multiselect and combobox. For a table of any size this is usually the better arrangement anyway, because search, sort and paging then happen server-side.

Wrapping the imperative API

The parts of the framework you call rather than declare: confirmations, toasts, modals: are worth a thin injectable so components depend on a typed service instead of a global. There is nothing to re-implement; these are a few lines each.

@Injectable({ providedIn: 'root' })
export class UiDialog {
  private zone = inject(NgZone);

  /** Resolves true if the user confirmed. */
  confirm(options: UIFramework.ConfirmOptions): Promise<boolean> {
    return UI.confirm(options).then((ok) => this.zone.run(() => ok));
  }

  toast(options: UIFramework.ToastOptions): void {
    UI.toast.show(options);
  }
}
async remove(licence: Licence) {
  const ok = await this.dialog.confirm({
    title: 'Revoke licence',
    message: `Revoke ${licence.number}? This cannot be undone.`,
    confirmText: 'Revoke',
    variant: 'danger',
  });
  if (ok) this.api.revoke(licence.uuid).subscribe();
}

The NgZone.run() is belt-and-braces while zone.js is in play, and required once the application moves to zoneless change detection. The same wrapping applies to any framework callback that ends up updating a signal or a component field.

Scoped CSS and generated markup

Angular’s emulated view encapsulation works by stamping a _ngcontent-* attribute onto the elements in a component’s template, and rewriting that component’s styles to match it. Markup the framework generates at runtime: a table toolbar, a multiselect panel, a toast: never passes through that template, so it carries no such attribute and component-scoped rules do not reach it.

Keep ui-framework.css where it is, in the global styles array, and put overrides for generated markup either in a global stylesheet or in a component that sets encapsulation: ViewEncapsulation.None. Reaching for ::ng-deep works too, but it is deprecated and global in effect regardless of how it reads.

TypeScript

The package ships hand-written definitions at dist/ui-framework.d.ts, declaring the global UI object and a UIFramework namespace for the option and result types. They are deliberately partial: internal fields are not declared, so if something does not typecheck it is probably not public API.

// tsconfig.app.json
{
  "compilerOptions": {
    "types": ["ui-framework"]
  }
}

Or, if you would rather not touch types, add /// <reference types="ui-framework" /> to a single file in the project.

React, Vue and Svelte

Nothing on this page is Angular-specific except the names. The framework holds no reference to any host framework; it reacts to nodes entering and leaving the document, which is a property of the DOM rather than of Angular.

React implements onChange on the native input event, so the same UI.fireChange() pair that satisfies Angular satisfies React, and Vue’s v-model listens for input on text fields and change on selects. Call UI.observe(document.body) once after mount, and use the same refresh calls when data arrives after render.
