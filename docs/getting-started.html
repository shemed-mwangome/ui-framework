Installation

Start without changing your existing theme.

The framework uses the ui- prefix and scoped base styles, making it suitable for any server-rendered application — JSP, PHP, Rails, Django, or plain static HTML — that already uses Bootstrap, CoreUI, or custom master styles.

New here? Try it in 10 seconds

No server, no build step, no account. Download or clone the repository, then double-click quick-start.html in the project root to open it directly in your browser (no http:// needed — a plain file:// path works). It loads the two bundled files and shows a working button, so you can confirm everything is wired up before touching any of your own pages.

How it works, in plain terms

If you've never used a component library before, here's the whole mental model — there isn't more to it than this:

  • CSS classes style things. Every class starts with ui- (e.g. ui-btn, ui-card) specifically so it can't collide with your existing CSS. Write plain HTML and add these classes the same way you'd add any CSS class.
  • data-ui-* attributes trigger behavior — you write zero JavaScript. For example, a button with data-ui-modal-open="#myModal" opens a modal when clicked. The framework's JavaScript file scans the page for these attributes once it loads and wires up the click handlers for you automatically.
  • Nothing needs to be "initialized" for content that's already in the page when it loads. You only call UI.init(element) manually if you insert new HTML with JavaScript after the page has loaded (see JavaScript API).

That's it. Everything else in these docs is just the full list of available ui-* classes and data-ui-* attributes and what each one does.

Option 1: single CSS and JavaScript

The easiest deployment option. Copy the complete framework folder into your static resources and include the two files, loaded after Bootstrap/CoreUI/your existing stylesheet if you have one — see using alongside Bootstrap below for why the plain bundle, not ui-framework.layered.min.css, is the right default even then.

<link rel="stylesheet" href="/ui/static/ui-framework/dist/ui-framework.min.css">

<!-- Page content -->
<body class="ui-scope">
  ...
</body>

<script src="/ui/static/ui-framework/dist/ui-framework.min.js"></script>

Option 2: reusable modules

Load only the component styles and scripts needed by a page. Always load tokens and core first.

<link rel="stylesheet" href="/ui/static/ui-framework/src/css/00-tokens.css">
<link rel="stylesheet" href="/ui/static/ui-framework/src/css/01-base.css">
<link rel="stylesheet" href="/ui/static/ui-framework/src/css/05-buttons.css">
<link rel="stylesheet" href="/ui/static/ui-framework/src/css/06-forms.css">

<script src="/ui/static/ui-framework/src/js/00-core.js"></script>
<script src="/ui/static/ui-framework/src/js/05-modal.js"></script>

Using alongside Bootstrap or an existing stylesheet

Every class is prefixed ui-, so there are no class-name collisions with Bootstrap, CoreUI, or your own CSS. The part that can collide is more basic than that: both frameworks style bare HTML elements — table, h1–h6, button, form controls — before either one's classes are even involved.

With the plain bundle (ui-framework.css / .min.css), whichever stylesheet's <link> comes last in your <head> wins ties on those element selectors — not per component, the whole file. Load it after Bootstrap and every <table> on the page, including ones you never gave ui-table, can start picking up this framework's default border and padding instead of Bootstrap's. Load it before, and the reverse happens. It isn't a crash, just a silent, page-wide restyle of elements you didn't touch, and the direction depends entirely on link order.

ui-framework.layered.css (and .layered.min.css) exists for that specific problem: it wraps every rule in @layer ui-base, ui-components, ui-utilities, so this framework's bare-element styles unconditionally lose to Bootstrap's regardless of link order.

!
The layered bundle is not the safe default for Bootstrap coexistence

The rule cuts both ways, and the direction that bites is the common one: an unlayered stylesheet always beats a layered one, regardless of selector specificity — not just for the element-selector ties above, but for every declaration. Bootstrap 4 ships plenty of unlayered, low-specificity element resets that this framework's own component classes would normally beat under ordinary cascade rules — e.g. bare label{display:inline-block}, which every option row in data-ui-multiselect and every .ui-checkbox/.ui-radio pair is built on. Load the layered bundle, and that unlayered Bootstrap rule silently wins anyway, breaking layout that the plain bundle would have gotten right for free. Reach for the layered bundle only when you specifically need to guarantee a win against a legacy rule that's more specific than this framework's own selector (an ID, a long descendant chain) — not as a general-purpose "coexist with Bootstrap" default.

So with nothing more than:

<link rel="stylesheet" href="bootstrap.css">
<link rel="stylesheet" href="dist/ui-framework.layered.min.css">

Bootstrap's base styles stay untouched no matter which of those two lines comes first. Component classes still resolve their own internal styling normally (a .ui-btn looks like a .ui-btn either way) — layering only changes who wins when the same bare element is targeted by both frameworks, which is a narrower guarantee than "everything from this framework works."

If you do need the layered bundle for that narrower case, and still want one specific component from this framework to win over a Bootstrap style, declare the order yourself, once, at the top of your own stylesheet:

@layer bootstrap, ui-base, ui-components, ui-utilities, app-overrides;

Precedence is then exactly what you wrote, left to right, later wins — no specificity math, no !important. Keep your own overrides inside a declared layer (app-overrides above) rather than leaving them unlayered, or the "unlayered always wins" rule will apply to them too.

Server-side integration

Load the framework after your existing CSS. Wrap new content in ui-scope to apply the optional base typography safely. The paths below are plain HTML — substitute your own templating syntax (JSTL's <c:url>, Thymeleaf, PHP includes, an asset helper, etc.) to resolve them.

<link rel="stylesheet" href="/static/ui-framework/dist/ui-framework.min.css">

<main class="ui-scope">
    <!-- UI Framework components -->
</main>

<script src="/static/ui-framework/dist/ui-framework.min.js"></script>

See examples/jsp-integration.jsp in the repository for one worked example.

Theme customization

Override design tokens after the framework stylesheet. Components automatically use the new values.

<style>
:root {
  --ui-primary: #143b6b;
  --ui-primary-hover: #0d2d55;
  --ui-success: #3cb371;
  --ui-radius-3: 8px;
  --ui-font-sans: "Open Sans", Arial, sans-serif;
}
</style>
i
Dark theme

Set data-ui-theme="dark" on the HTML element, or use a button with data-ui-theme-toggle.

Troubleshooting

Common first-time issues, in the order you're likely to hit them.

Everything looks unstyled (no colors, no spacing).

The CSS file isn't loading. Open your browser's devtools → Network tab and check that ui-framework.min.css returned 200, not 404. The path in your <link> tag is relative to the HTML file it's written in — a common mistake is copying a snippet without adjusting the path for where your file actually lives.

Clicking a button does nothing (modal, dropdown, tabs, etc.).

The JavaScript file isn't loaded, or it's loaded before the HTML it needs to scan. Make sure <script src="...ui-framework.min.js"> comes right before </body>, after all the markup it controls. Also check the browser console for errors — a JS error earlier on the page can stop the rest of the script from running.

A component's opening/closing ID doesn't match.

Things like data-ui-modal-open="#myModal" must exactly match the target's id="myModal", including the #. A typo here fails silently — no error, the button just does nothing.

A checkbox/radio/switch still looks like a plain browser checkbox.

The <label> must come immediately after the <input> in the HTML (see Selection) — the styling is applied via a CSS sibling selector, so anything in between (a wrapping <div>, extra whitespace-only elements) breaks it.

A floating label isn't floating.

The input needs placeholder=" " (a single space, not empty) for the CSS :placeholder-shown check to work, and the <label> must come after the input (see Forms).

Content I added with JavaScript doesn't work (new modal, new tabs, etc.).

The framework only scans the page once, when it first loads. If your own script inserts new HTML afterward, call UI.init(theNewElement) to wire it up — see Initialization.
